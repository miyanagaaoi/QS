## 1. 项目概述

### 1.1 背景

我方目前用 Excel 表格（见 `doc/示例.xls`）向多家供货商询价：我方人员把材料清单做成一张表，逐个发给供货商，供货商在表里填价格和到货日期后回传，我方再人工汇总比价。现状问题：

1. **版本失控**：多个 Excel 文件在多台电脑间传来传去，改到第几版无法追溯。
2. **汇总靠手工**：多家回传的价格要人工对齐到同一张表上比价，行数一多极易串行、漏行、算错。
3. **过程无留痕**：谁在什么时间报了什么价、改过几次，事后无法追溯。
4. **报价泄露风险**：用邮件或聊天工具群发时，容易让供货商互相看到对方报价。

### 1.2 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 询价单线上化管理，替代 Excel 往返 | 新建/导入询价单后，供货商在线填报，回收率 100% 可查 |
| G2 | 多供货商报价自动汇总比价 | 统计报表一键给出每行物料各家报价、最低价、差额，免人工对齐 |
| G3 | 报价过程全程留痕 | 每次改价留存历史版本，关键操作有日志 |
| G4 | 供货商之间报价完全隔离 | 供货商接口层面无法获取他方报价数据（含最低价） |
| G5 | 交付即用、零运维 | Docker Compose 一条命令起服务，数据卷备份即可恢复 |
| G6 | **供货商在手机上就能完成报价** | 手机浏览器从"收到单据"到"提交报价"全流程无需求助 PC；核心路径可用性测试通过率 100% |
| G7 | **一套代码适配 PC 与手机** | 不维护两套前端页面；PC / 平板 / 手机三档断点下无横向溢出、无遮挡、无非可点元素 |

### 1.4 术语表

| 术语 | 定义 |
|---|---|
| 询价单（RFQ） | 我方创建的一张采购询价单据，包含表头信息与若干明细行 |
| 报价单（Quotation） | 供货商针对某张已发布询价单填报的价格结果集合，**一家供货商一份** |
| 询价明细行 | 询价单里的一条物料需求（材料名称、规格型号、单位、数量等） |
| 报价明细行 | 供货商对某条询价明细行填写的价格结果（含税单价、税率、MOQ、交期、到货日期） |
| 分派 | 发布时把询价明细行复制给指定供货商，形成该供货商可填报的报价行 |
| 改价历史 | 供货商每次保存报价时自动留存的上一个版本快照 |

## 2. 需求确认结论（已与需求方逐项确认）

| 议题 | 确认结论 |
|---|---|
| 单据模型 | **一张询价单按供货商拆成多份独立报价单**，各供货商只看到自己那一份 |
| 价格维度 | 含税单价（默认人民币 CNY，两位小数）+ **是否含税开关 / 税率** + **最小起订量 MOQ** + **交货周期（天）** |
| 报价保密 | **完全隔离**：供货商看不到他方价格，也看不到当前最低价；报表仅我方可见 |
| 状态流转 | 简化三态：**草稿 → 已发布 → 已截止**（不做多轮议价状态） |
| 改价规则 | 已截止前供货商**可多次改价**，每次保存**自动留存一个历史版本** |
| 明细行标识 | 增加**系统内部明细行 ID（UUID）**，不展示给用户，用于避免"名称+规格"匹配错行 |
| 明细扩展字段 | **行备注 / 行附件**（不做物料编码列、不做品牌列） |
| 账号角色 | 两类：**我方人员（管理员 / 采购员）+ 供货商账号** |
| 账号能力 | 启用/停用、重置密码、**批量导入供货商账号**、关键操作日志；**首次登录强制改密** |
| 基础数据字典 | **计量单位字典、税率字典、供货商档案**（名称/联系人/电话/邮箱/地址）；项目列不建字典，建单时手输 |
| 通知 | **不做任何消息通知**，纯内网登录可用 |
| 导入导出 | 我方 Excel 导入询价明细、我方导出询价单/报价结果为 .xlsx |
| 使用规模 | 我方人员 3~4 人，供货商 ≤ 50 家，同时在线 < 20 |
| **终端与响应式** | **同一套 Web 响应式适配，不另做原生 App / 小程序**；三档断点：手机 < 768px、平板 768~1199px、桌面 ≥ 1200px；**核心原则：供货商侧以手机为主要终端必须完整可用，采购/管理侧以桌面为主要终端** |
| 手机端能力边界 | 手机上**必须完整可用**：登录改密、待报价列表、报价填报与提交、查看自己的历史报价、行附件拍照上传、查看我方备注<br>手机上**可只读或简化，不要求完整操作**：询价单新建与 Excel 导入、比价报表全量视图、账号管理与批量导入、字典维护（这些以 PC 为主，手机端给出可读视图 + 引导到 PC 的提示） |
| 部署 | **Linux + Docker Compose 为主** |
| 运行环境 | **Python 3.12**（实测落地版本；PRD 原选型为 3.11+，本机原先探测到的 3.14.7 实为另一处 PATH，实际可用解释器为 3.12.14，见 14.3 变更说明） |
| 交付物 | 本次仅交付 PRD 文档；代码待 PRD 评审通过后启动 |

## 3. 用户角色与权限

### 3.1 角色定义

| 角色 | 身份 | 典型人员 | 说明 |
|---|---|---|---|
| 管理员 `admin` | 我方人员 | 采购主管 / IT | 拥有全部权限，含账号管理、字典维护、全部询价单可见 |
| 采购员 `buyer` | 我方人员 | 采购员 | 创建与管理**自己创建的**询价单，可查看自己单据的报价与报表 |
| 供货商 `supplier` | 外部人员 | 供货商业务员 | 只能查看/填报**分派给自己公司**的已发布或已截止询价单 |

> 我方 3~4 人：建议 1 名管理员 + 2~3 名采购员。供货商账号与"供货商档案"一对一绑定（一个供货商可有多人账号，本期默认 1 个）。

| 功能 | 管理员 | 采购员 | 供货商 |

| 发布 / 撤回 / 截止询价单 | ✅ 全部 | ✅ 仅自己创建 | ❌ |
| Excel 导入询价明细 | ✅ | ✅ | ❌ |
| 查看询价单列表 | ✅ 全部 | ✅ 仅自己创建 | ❌ |
| 查看某张询价单的报价情况 | ✅ | ✅ 仅自己创建 | ❌ |
| 填报 / 修改自己的报价 | ❌ | ❌ | ✅ 仅分派给本公司的单 |
| 查看他方报价、最低价、比价 | ✅ | ✅ 仅自己创建 | ❌ **（硬约束）** |
| 报价单统计报表 | ✅ 全部 | ✅ 仅自己创建 | ❌ |

| 查看操作日志 | ✅ | ❌ | ❌ |
| 修改自己的登录密码 | ✅ | ✅ | ✅ |

### 3.3 关键可见性约束（不可妥协项）

1. **接口层强制隔离**：供货商调用任何报价/询价接口时，服务端必须按 `询价单 → 分派 → 当前登录供货商` 过滤；查询条件中若含他方供电商标识直接拒绝（403），**不得依赖前端隐藏**。
2. **最低价不外泄**：统计报表接口与聚合查询对供货商角色一律 403。
3. **列表范围**：供货商登录后的"报价单"列表 = 分派给自己的、且状态为「已发布/已截止」的询价单。草稿状态的询价单对供货商完全不可见（即便已被分派）。
4. **我方可见范围**：采购员仅可见 `created_by = 当前用户` 的询价单；管理员可见全部。
5. **附件隔离**：行附件中我方上传的图纸对已分派供货商可见；供货商上传的附件仅我方与上传者本人可见。

## 4. 核心业务流程

### 4.1 全流程主链路

```
① 我方：新建询价单（手工录入 或 Excel 导入明细）
        ↓
② 我方：选择项目、设定报价截止时间、勾选受邀供货商
        ↓
③ 我方：点击「发布」→ 系统为每个受邀供货商生成一份独立报价单（状态：待报价）
        ↓
④ 供货商：登录 → 看到"待报价"列表 → 打开填报页
        ↓
⑤ 供货商：逐行填写 含税单价 / 税率 / MOQ / 交货周期 / 到货日期 / 备注，可上传行附件
        ↓
⑥ 供货商：点击「保存」→ 生成/更新报价 + 留一条改价历史（截止前可反复改）
        ↓
⑦ 我方：在「报价单」列表看进度（已报价 x / y 家、未报价清单）
        ↓
⑧ 我方：到截止时间或手动「截止」→ 报价单锁定，供货商不可再改
        ↓
⑨ 我方：进入「报价单统计报表」比价、导出 .xlsx，完成定标决策
```

### 4.2 状态机

**询价单状态**

| 状态 | 进入方式 | 允许操作 | 供货商可见 |
|---|---|---|---|
| 草稿 `draft` | 新建、导入后 | 编辑表头/明细、增删供货商、导入、发布、删除 | ❌ 不可见 |
| 已发布 `published` | 草稿点击发布且校验通过 | 截止、导出、查看报价进度；**明细行禁止增删改** | ✅ 可见可填报 |
| 已截止 `closed` | 手动截止 或 到达截止时间自动截止 | 查看、导出、统计；**报价与明细全部锁定** | ✅ 仅可查看自己的报价 |

**供货商报价单状态**

| 状态 | 说明 |
|---|---|
| 待报价 `pending` | 分派已生成，供货商尚未提交或尚未填写任何一行 |
| 报价中 `partial` | 已填写部分行并保存 |
| 已报价 `quoted` | 全部明细行均已填写并保存（至少含单价） |

> 报价单状态由系统按填写完整度自动计算，不需人工维护。截止后状态冻结。

### 4.3 自动截止

- 询价单表头含「报价截止时间」，发布时必填，且必须晚于当前时间。
- 建议实现方式：每次读取/写入询价单时惰性判断 `deadline < now()` 且状态为 `published`，则自动置为 `closed`；同时由服务端定时任务（每 1 分钟）兜底扫描。
- 自动截止必须写一条操作日志（操作人记为 `system`）。

#### 5.1.2 新建 / 编辑询价单页

**表头字段**

| 字段 | 类型 | 必填 | 校验/说明 |
|---|---|---|---|
| 单据名称 | 文本 ≤ 100 | ✅ | 默认「{项目}-{YYYYMMDD}询价」 |
| 项目 | 文本 ≤ 100 | ✅ | 自由输入，提供历史值联想（不建字典） |
| 报价截止时间 | 日期时间 | ✅ | 必须晚于当前时间；发布时再次校验 |
| 受邀供货商 | 多选 | ✅ | 从供货商档案中选，至少 1 家 |
| 备注 | 文本 ≤ 500 | ❌ | 对供货商可见的说明（如付款方式、交货地点） |
| 内部备注 | 文本 ≤ 500 | ❌ | **对供货商不可见**，仅我方查看 |

**明细行字段（对齐 `doc/示例.xls`）**

| 列序 | 列名 | 类型 | 必填 | 谁填 | 说明 |
|---|---|---|---|---|---|
| 1 | 序号 | 整数 | 自动 | 系统 | 行内顺序号，前端自动生成 |

## 6. 数据模型

### 6.1 实体关系

```
supplier (供货商档案) 1 ──< user (供货商账号)
user (我方账号) 1 ──< rfq (询价单)
rfq 1 ──< rfq_line (询价明细行, 冻结副本)
rfq 1 ──< rfq_supplier (分派: 每个受邀供货商一条)
rfq_supplier 1 ──< quote_line (报价明细行: 每条询价明细行 × 该供货商)
quote_line 1 ──< quote_history (改价历史)
user 1 ──< audit_log
unit_dict / tax_dict / supplier 为独立字典表
```

### 6.3 关键约束

1. `rfq.rfq_no` 唯一，按日流水生成，需处理并发（数据库唯一索引 + 重试）。
2. `rfq_supplier` 对 `(rfq_id, supplier_id)` 唯一。
3. `quote_line` 对 `(rfq_supplier_id, line_uid)` 唯一。
4. 金额统一 `DECIMAL`，**禁止用 float**。
5. 时间统一口径：**应用统一使用北京时间（UTC+8）的 naive datetime**，数据库与接口返回均为此口径，接口返回的 `datetime` 字符串**可直接展示，前端不做时区换算**。
   - 决策依据：本系统为内网单时区部署（见 Q1），管理员在界面填写的「报价截止时间」本身就是北京时间。若按 UTC 存储，界面填 18:00 会变成 UTC 18:00（实际北京时间次日 02:00），实测导致**截止时间比用户意图晚 8 小时执行**。
   - 实现约定：`app.models.app_now()` 为唯一时间源（`utcnow` 仅作兼容别名保留）；`utils.to_app_tz()` 负责把带时区偏移的入参（如 `+08:00`）归一化到北京时间后再去掉 tzinfo；`is_deadline_passed` / `remaining_seconds` 与业务时间同基准比较。
   - 遗留权衡：若将来需支持多时区或与按 UTC 对接的外部系统集成，应改为「存储带 tzinfo 的 UTC + 接口层显式标注时区」，届时前端需同步恢复时区换算逻辑。
6. 所有查询必须带软删除/状态过滤，不存在物理删除报价数据。

| web | nginx:alpine（内含构建后的前端静态资源） | 宿主 80 或 8080 | — |

- `docker-compose.yml` 提供 `db`（PostgreSQL 16）为可选 profile，切换到 PG 时只需改 `DATABASE_URL` 并执行迁移。
- 备份策略：每日定时复制 `data/` 目录（SQLite）或 `pg_dump`（PostgreSQL）到备份盘，保留 30 天。
- 首次启动自动建表 + 创建默认管理员账号（`admin` / 随机初始密码打印到容器日志，强制首次登录改密）。

### 9.5 已知技术风险

| 风险 | 说明 | 应对 |
|---|---|---|
| ~~Python 3.14 生态兼容~~ **已排除** | 实际落地 Python 3.12，`requirements.txt` 全部依赖均从 PyPI 正常安装（fastapi 0.115.6 / SQLAlchemy 2.0.36 / pydantic 2.10.4 / bcrypt 4.2.1 / xlrd 2.0.1 等），未出现 wheel 缺失或需编译的情况 | 版本已在 `requirements.txt` 锁定；SQLite 场景不使用 asyncpg |
| `.xls` 读取 | 示例文件为 OLE2 BIFF 格式，openpyxl 不支持 | 引入 xlrd==2.0.1 兼容读取，或统一要求 .xlsx 模板（验收时以实际文件回归） |
| SQLite 并发写 | 20 人同时在线时可能出现 `database is locked` | 开启 WAL 模式 + `busy_timeout`；写操作短事务；规模增长即切 PostgreSQL |
| 比价报表性能 | 50 家 × 2000 行的交叉表计算量大 | 视图 A 限制单张单据查询；必要时在 `quote_line` 上建 `(rfq_supplier_id, line_uid)` 索引，聚合结果可按单据缓存（TTL 30s） |
| **移动端 Element Plus 组件适配** | Element Plus 的 `el-table`、`el-dialog` 在窄屏表现一般（表格挤压、弹窗超高、日期选择器超宽） | 宽表统一走 `DataTable.vue` 双形态封装；弹窗在手机端改用全屏或底部弹层；日期/下拉在小屏限制最大宽度并按 viewport 定位 |
| **手机端大量录入体验** | 20 行物料在手机上逐行滚动填价容易疲劳、易漏填 | 报价页默认只展开"单价"，其余字段折叠；底部固定栏实时显示"已填 x/y 行"；提交前统一列出漏填行号 |
| **iOS 数字键盘与缩放** | `type="number"` 在部分机型缺小数点；输入框字号 <16px 会触发页面自动放大 | 单价用 `type="text" + inputmode="decimal"`；输入框统一 ≥16px；`viewport` 不加 `maximum-scale=1`（保留无障碍缩放） |
| **微信内置浏览器差异** | 微信 WebView 对文件下载、`localStorage` 清理策略、`beforeunload` 行为不一致 | 导出类功能在微信内提示"请在系统浏览器打开下载"；本地草稿优先 IndexedDB 并做降级；不依赖 `beforeunload` 保存 |
| **真机验证成本** | 仅用桌面浏览器模拟器无法发现真实键盘、滚动、拍照问题 | 验收强制真机（见 FR-RWD-30），测试机建议保底：1 台 iPhone + 1 台 Android + 1 台国产安卓（微信） |

## 10. 移动端与响应式设计规范

### 10.1 断点定义（全站统一）

| 代号 | 范围 | 目标设备 | 布局基线 |
|---|---|---|---|
| `xs` 手机 | `< 768px` | iPhone SE 375×667 起，常见 390×844 / 412×915 | 单列；导航抽屉；列表卡片化；宽表内部横向滚动 |
| `sm` 平板 | `768px ~ 1199px` | iPad 竖屏 768×1024、横屏 1024×768 | 主流两栏；导航折叠为图标栏；表格可显示 6~8 列 |
| `md` 桌面 | `≥ 1200px` | 1366×768、1920×1080 | 左侧导航常驻；表格显示全部列 |

- 断点值集中定义在 `styles/breakpoints.scss`，**禁止在业务组件里散落硬编码像素值**。
- 采用 **Mobile First** 编写顺序（默认写手机样式，用 `@media (min-width: 768px)` 向上增强），避免"桌面样式被手机继承后到处打补丁"。
- JS 侧通过 `composables/useBreakpoint` 暴露 `isMobile / isTablet / isDesktop` 响应式布尔值，用于"同一数据换组件形态"（如表格 ↔ 卡片）。
- **不做 UA 嗅探判断设备**，一律以视口宽度为准（平板横竖屏、桌面浏览器缩窄窗口都能正确响应）。

### 10.3 供货商报价填报页（手机端）设计细则

> 这是手机端最关键、也最容易做坏的页面，单独规范。

**单条物料卡片结构**

```
┌─────────────────────────────────────────┐
│ ① 订书机                                  │   ← 材料名称（主标题，加粗）
│   得力，小 · 个 · 采购 40                  │   ← 规格型号 · 单位 · 采购数量（次要信息）
├─────────────────────────────────────────┤
│  含税单价 *                               │   ← 唯一默认展开的输入项
│  [        113.00            ] 元/个       │   ← 占满宽度，大字，inputmode=decimal
├─────────────────────────────────────────┤
│  ▸ 更多报价信息（税率 / MOQ / 交期 / 到货日期 / 备注 / 附件） │  ← 默认折叠
└─────────────────────────────────────────┘
```

**关键规则**

1. **默认只展开"含税单价"**：拾行物料在手机上滚动长度可控，减少漏斗流失。
2. 已有填写内容的行，卡片右上角显示"已填"标识（绿色），未填为灰色，**扫一眼即可知道漏了哪几行**。
3. "更多报价信息"折叠区展开后，内部字段单列纵向排列，每个输入框独占一行，标签在输入框上方（不做左右并排，避免标签被压缩换行）。
4. **底部固定操作栏（StickyBar）**：左侧实时"已填 7/10 行"，右侧「保存」「提交报价」两个按钮；提交为主按钮（实心），保存为次按钮；滚动过程中始终吸底，含 `safe-area-inset-bottom` 适配 iPhone 底部横条。
5. 未填行可在底部栏点击"跳到下一个未填"快速定位。
6. 附件区在手机端显示为"相机图标 + 相册图标"，点击直接调起相机或相册；已上传附件显示缩略图 + 删除按钮；单张压缩至 ≤2MB。
7. 报价截止后：所有输入框 `disabled`，底部栏替换为灰色提示条"报价已于 2026-10-15 18:00 截止"。
8. **空状态**：若该单据 0 行物料（异常数据），显示"该询价单没有需要报价的物料，请联系采购方"。
9. **长清单分段**：明细行 > 10 行时，手机端按每 10 行分段展示（"第 1~10 行 / 共 43 行" + 上一段/下一段），底部栏的"已填 x/y"始终按整单统计（不是当前段），避免供货商误以为只需填完当前段。
10. **日期字段**：待报价数量多或需限定取值范围（如不得早于今天）时，允许改用 `el-date-picker` 移动端面板形态；但**禁止在小屏弹出超宽的桌面级日期面板**，且任何情况下都要保证 iOS 上不会被系统原生控件遮挡。实现时二选一并记录在代码注释中（对应 Q12 的定稿）。

### 10.5 移动端性能预算

| 指标 | 目标 | 措施 |
|---|---|---|

### 14.1 与 `doc/示例.xls` 的差异说明

示例文件的表结构在线上化后的映射关系：

| 示例列 | 线上化处理 |
|---|---|
| 序号 | 保留，自动生成 |
| 材料名称 / 规格型号 / 单位 / 项目 / 采购数量 | 保留，我方录入或导入 |
| 供应商（示例值为"自动填写"） | 不再作为明细列人工填写；改为「一张单拆成多家独立报价单」，各供货商登录后只看到自己那份，供货商列仅在比价报表中横向展示 |
| 价格（示例为 ￥两位小数格式） | 拆为「含税单价 + 是否含税/税率 + 不含税单价（自动算）」，并新增 MOQ、交货周期 |
| 到货日期 | 保留，供货商填写；另增"交货周期（天）" |
| 备注（示例值为"填写变动或替代方案"） | 保留为行备注，作为供货商填写替代方案的说明位 |

补充说明：示例 `.xls` 实为 OLE2 容器（内部含 BIFF Workbook 流，三个工作表 Sheet1/2/3，仅 Sheet1 有数据：1 行表头 + 1 行示例数据），并内嵌了人民币/美元数字格式定义。本文档的表头与示例值均据此实际解析得出，非推测。

### 14.5 安全权衡记录：首次登录改密改为默认关闭（2026-10）

**变更内容**：原 FR-ACC-13 要求"新建账号首次登录强制修改密码"（`must_change_password` 由系统写死为 `true`）；
现改为**按账号开关控制，默认关闭**（`FR-ACC-15`），只有建号时显式开启才强制改密。

**为什么改**：需求方在验收阶段提出该策略过严 —— 内网小团队（我方 3~4 人、供货商 ≤50 家）里，
管理员建号后通常当面/电话告知初始密码，强制改密反而增加了"供货商记不住新密码、反复找管理员重置"的成本，
实测在联调期间已出现因强制改密导致登录失败沟通成本上升的情况。

**放宽后的风险**：
- 初始密码由管理员设定并在传递过程中可能被第三方看到，若账号长期沿用该密码，泄露面更大；
- 失去"首次登录必须改密"这一强约束后，密码长期不变的风险上升。

**保留的兜底措施**（因此风险可控）：
1. 密码强度仍强制校验：8~20 位且至少含字母与数字（`_check_password_strength`）；
2. **重置密码仍强制改密**（`FR-ACC-05` 未放宽）：管理员重置后 `must_change_password=true`，
   该账号下次登录除改密接口外一律 40101；
3. 账号可随时**停用**（停用后立即无法登录、已登录会话在下次请求即失效），不支持删除以保留可追溯性；
4. JWT 携带**密码指纹**，任何改密/重置都会让旧 token 立刻失效，无法长期复用旧凭据；
5. 账号列表对 `must_change_password=true` 的账号显示「需改密」标记，管理员可据此巡检；
6. 建号、重置、启停用全部写入操作日志（含操作人与 IP）。

**使用建议**：
- 我方账号（尤其管理员）建议建号时**显式开启**强制改密；
- 供货商账号按实际沟通方式决定；若初始密码通过不安全渠道传递，建议开启。

**如需回退**：将 `schemas.InternalUserCreate.must_change_password` 与
`schemas.SupplierAccountCreate.must_change_password` 的默认值改回 `True` 即可恢复原策略，
前端开关无需改动（开关打开即为原行为）。
